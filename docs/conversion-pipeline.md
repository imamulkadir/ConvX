# Conversion and verification plan

1. Stream DOCX into private staging; verify ZIP/OOXML type, quotas and relationship safety.
2. Inventory revisions across supported stories and validate provider capability. Accept changes on a copy; save accepted DOCX. Independently rescan all package XML, verify retained/deleted text, story/table structure and media relationships. Unknown revisions fail safely.
3. Render that accepted DOCX to PDF through the selected qualified provider. Check parseability, nonempty pages/text, geometry, fonts and completeness. With an authorized reference, compare every page's page count, boxes, reading content, positions and renders. Strict PDF failures stop before extraction. Without a source reference, record that source-to-PDF fidelity is unproven; profiles that require it fail rather than claim verified fidelity.
4. Analyze the generated PDF with PyMuPDF into the versioned layout model. OOXML provides semantic hints only. Reject unmapped glyphs, omitted disclosure or ambiguous reading order when unresolved.
5. Reconstruct using approved EDGAR markup with searchable text. Plan tables without nesting, logical text and explicit incompatibilities for layouts that permitted markup cannot reproduce. No page screenshots as disclosure replacements.
6. Extract/normalize graphics only. Prefer GIF for palette/line art and JPG for photographic content after image-specific review; preserve aspect, crop, color and geometry. Assign deterministic `image001.jpg`/`.gif` names. Composite only graphic regions, never ordinary disclosure text. Do not assume DOCX PNG assets are final-format compliant.
7. Validate actual HTM bytes, parsed markup, CSS, URLs and image files using an approved manual-derived rule profile. An unresolved required rule prevents strict success.
8. Render with pinned Chromium/Playwright at fixed 96 CSS px/in and controlled device scale; render PDF at the corresponding physical scale. Capture every page boundary and overflow, not only viewport screenshots. Use identical licensed fonts where available; fonts embedded in PDF do not authorize web embedding.
9. Compare exact disclosure content/order, character/line/table/image geometry and per-page pixels. Preserve raw images and difference masks. Antialiasing classification must be narrow, independently evidenced and cannot forgive text displacement or missing strokes. Strict success means zero unexplained discrepancies; do not choose a permissive scalar pixel threshold and call it pixel-perfect.
10. Attempt bounded safe corrections only; re-run compliance, content and visual checks after each change. Record unresolvable rotations, complex overlaps, font restrictions or page geometry as strict failures.
11. Validate final files and immutable gate hashes. Package only one `.htm` and exactly its referenced JPG/GIF images at root; reopen the ZIP and independently check CRC, members, paths, content signatures, references, duplicates and unreferenced files. No intermediate or report enters the ZIP.
12. Publish download atomically if owner, state, attempt, cancellation and expiration checks still pass.

Outer ZIP retains the uploaded basename after rejecting unsafe client filenames; it is a download container rather than a submitted EDGAR document. Content-Disposition must use safe encoding. Internal HTM name is separate: sanitize to the permitted alphabet, make the first character alphanumeric, shorten deterministically using a source-name hash within 32 characters including `.htm`, and check collisions. Exact algorithm and test vectors belong to Stage 8. Do not use the illustrative overlength filename in the master instructions literally.

Regression plan: preserve original fixture hashes, clarify reversed DOCX roles, compare accepted semantic content including headers/footers, tables, notes, textboxes and graphics. Compare all 23 PDF pages at 612 x 792 points. Stage 1 inventories are not acceptance, rendering or visual regression tests.

Stage 3 execution update: DOCX roles are confirmed after the user's Stage 1 replacements. Revision content/structure and media preservation pass, but real free LibreOffice export fails all-page strict Word-reference fidelity. It stops before layout analysis/HTM generation. No paid provider is authorized. See [processing](docx-processing.md) and [qualification evidence](stage3-regression.md). This PDF-to-PDF gate is distinct from Stage 7's future HTM-to-PDF comparison engine.

Stage 4: after passing strict PDF validation, extract native text/typography, image geometry, vectors, table candidates and reading/region candidates into private schema-v1 `layout.json`. Bind it to PDF/validation hashes and renderer provenance. Unresolved blockers fail; otherwise stop at `awaiting_htm_generation`. Failed PDF validation never enters analysis. See [layout analysis](pdf-layout-analysis.md).

Stage 5: gated layout -> `generating_htm` -> private candidate and exact disclosure accounting, or explicit unsupported-layout failure. Image requests still require normalization; actual file compliance and browser-vs-PDF qualification remain pending. Successful candidate generation stops before SEC validation, never completing or publishing a ZIP. See [HTM reconstruction](htm-reconstruction.md).

Stage 6: candidate -> source-bound graphic materialization in private filing/ -> source-byte/decoded-asset validation. Reports contain source/candidate/file/registry hashes and explicit rule basis. Permission uncertainty fails instead of bypassing compliance. The actual one-page renderer positive PDF test now correctly records a downstream CSS permission failure; the 23-page Word fixture still stops at the PDF gate. No Stage 7 rendering or Stage 8 ZIP is implemented. See [SEC validation engine](sec-validation-engine.md).

Stage 7 adds comparing_formatting after the prior strict gates: isolated Chromium print/screen render -> independent content/font/geometry/resources/pixel checks -> private heatmaps/overlays/metadata. Any unexplained difference, missing page or incomplete evidence fails; source files are not modified. Inspection never authorizes packaging. Current Word and inline-style permission failures still stop earlier. See [visual validation](visual-validation.md).
