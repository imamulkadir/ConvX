# Stage 9 filing workspace

The UI is in `apps/web`: Next.js App Router, React JSX, Tailwind 4, DaisyUI 5 and Lucide. It performs uploads and review; Python workers still do every conversion. All dependencies are free. No hosted Site, Git write or deployment is performed.

## Run the UI

For everyday local use, run `.\.venv\Scripts\python dev.py` from the root and choose Use local access at the printed URL. This starts the UI, API and real local worker without Redis. See [one-command development](local-development.md). The separate-service commands below remain available.

Start the existing configured backend from the repository root (see [backend setup](backend-development.md) for installation, private tokens and schema configuration):

```powershell
.\.venv\Scripts\python -m app.cli init-db
.\.venv\Scripts\python -m uvicorn app.main:create_app --factory --host 127.0.0.1 --port 8000 --no-access-log
```

In another PowerShell terminal:

```powershell
Set-Location D:\Tools\ConvX\apps\web
npm.cmd ci
npm.cmd run dev
```

Open **http://127.0.0.1:3000**. Enter your own configured API access token and click Connect. The token stays in page memory and is never placed in a URL or browser storage. For an explicitly configured development backend with `CONVX_AUTH_MODE=local`, Use local access works over loopback. Never deploy local access or share a backend credential across users.

The API and UI run independently. Next rewrites `/api/v1/*` to the trusted `CONVX_API_URL` origin, forwarding the user's bearer header. It has no conversion route or shared service token. Default API origin is http://127.0.0.1:8000. To change it, copy `apps/web/.env.example` to `apps/web/.env.local` and edit the origin. Restart dev after changing it. Production rewrites capture this setting at **build time**, so set it before `npm run build`, then use `npm run start`. The current UI binds loopback by default.

To process queued uploads, independently run real Redis, the dispatcher and conversion worker as described in [backend setup](backend-development.md). API upload succeeds durably without a broker; jobs then remain queued. Native Windows Celery is not a supported production deployment. Existing renderer/reference configuration still applies; neither the UI nor the worker invents a reference or a whole-submission context. Stage 11 owns deployment infrastructure.

## Upload and review

Connect, choose or drop DOCX documents, review selected files, then click Start conversion. Selection checks extension, empty files, per-file, batch and aggregate limits from the authenticated API session endpoint. Backend admission remains authoritative. Actual transmitted upload progress is separate from conversion stages; 100% upload means the server may still be validating it. Partial batch errors retain accepted independent jobs and display individual rejection messages. No conversion percentage is fabricated.

The dashboard polls actual queued/running jobs without overlapping poll cycles and backs off on errors. Filter by processing, attention or download availability; search filenames and select a document. The detail panel shows stage evidence, validation results, manual references and remediation. Unknown failed stages do not imply completion. Delete/cancel requires a visible confirmation; retry is offered only for known resumable blocked capabilities and the API enforces eligibility.

Only opaque job IDs are retained in tab sessionStorage; filenames, disclosure and credentials are not persisted. Reconnect after a refresh to restore owned IDs; ownership is rechecked by the API. Use Reopen a previous job with its ID when needed. Disconnect clears the tab list and aborts owned requests. Theme preference alone uses localStorage. Previous-owner results cannot be applied after changing connection.

## Diagnostic previews

The owned preview endpoint accepts `kind=pdf|htm|overlay|difference` and a one-based page, or returns metadata with no kind. It serves current stopped attempts only, rejects expired/deleted/unowned jobs, validates original/PDF hashes and bounded paths, checks captured PDF bytes, and validates declared PNG structure/dimensions. No raw candidate HTML, DOCX, arbitrary file or active content is served. The current attempt/state is checked again before responding. Private/no-store headers apply.

PDF.js renders the actual generated PDF locally onto canvas using a locally copied pinned worker. Script evaluation and XFA are disabled; no annotations or hyperlinks are mounted. This preview is a review view, not the authoritative Stage 7 fidelity engine. HTM preview is the real Chromium screen capture already generated by Stage 7, not active untrusted markup. Print overlay and print-difference images are existing visual evidence. Canvas/capture display scale uses 96 CSS pixels per inch, adjusting for recorded capture DPI.

Controls support page navigation, 50–200% zoom, side-by-side view and proportional synchronized horizontal/vertical scrolling. Missing captures are explained honestly; the UI never bypasses earlier gates to generate a comparison. The native Word-reference case can expose its generated PDF after strict failure but has no downstream HTM capture. A successful diagnostic preview never enables a ZIP. Capture PNGs are internal review artifacts; serving them is not independent proof of final fidelity.

ZIP download uses the existing fully revalidated backend endpoint and its encoded filename. The button stays disabled unless current server eligibility says it is available. Actual successful fully qualified download remains unverified because genuine earlier PDF/SEC/screen gates fail. No SEC acceptance or pixel-perfect output is claimed.

## Accessibility and checks

Responsive desktop/mobile layout, light/dark modes, labelled controls, visible focus, reduced motion, a skip link, keyboard-operable roving tabs and native focus-trapped help dialog are included. Browser tests use axe WCAG A/AA checks on real empty/queued/failed UI states. Automated checks do not establish universal accessibility; manual assistive-technology and broader browser qualification remain future work.

```powershell
npm.cmd test
npm.cmd run check:format
npm.cmd run build
npm.cmd audit
npm.cmd run test:ui
```

UI tests start a disposable real API on 8766 and a production Next build/server on 3400, refusing to reuse existing servers. They stop their own servers afterward. The API uses temporary SQLite/private storage and test-only credentials; no Redis conversion is simulated. Native seed processing directly invokes the real worker with genuine LibreOffice self-reference evidence and retains the actual SEC failure. Without a configured native renderer, only the native PDF review branch is unavailable; the test seed records that limitation. Do not use the test launcher as a development/production server.

Windows native export failed in the longer system TEMP/UUID workspace during initial UI qualification; a shorter disposable workspace under ignored `var/stage9` succeeded. This does not qualify arbitrary Windows path lengths. Keep development storage paths short; robust deployment/path isolation remains outstanding. No provider output was fabricated or substituted to make the test pass.

Screenshots/traces and seed artifacts stay ignored under `var/stage9` and UI test-results. Original regression fixtures are unchanged. See [test history](test-history.md) and [project status](../PROJECT_STATUS.md).
